Core Rule
Do Not Audit the Narrative Directly

The polished HTML pages are where the strongest positions are stated. They are the right place to understand the thesis. They are not the right place to decide whether a metric is true.

claim page -> raw artifact or code path -> rerun or inspect -> pass / revise / demote
Working Split
Use Two Layers On Purpose
  • Claims layer: the formal HTML pages in docs/
  • Evidence layer: experiment dirs, harnesses, raw results, and runtime code
  • Interpretation layer: papers and position pages explaining what the findings mean
Discipline for the next few days: every strong number in the docs gets placed into one bucket: rerunnable now, artifact-backed, theory/open, or external bridge.
Section 2

Evidence Classes

Rerunnable Now
Best Case

You can run the harness yourself and compare the result against the claim.

Artifact-Backed
Acceptable If Traceable

The result already exists on disk, but you may not have re-run it recently.

Theory / Open
Do Not Treat As Measured

Mathematical results, conjectures, and architectural consequences.

External Bridge
Separate From Your Data

Claims that rely on outside papers or outside model vendors.

Claim Type Primary Source What Counts As Validation What Does Not
Empirical metric Raw results, scripts, output files Reproduced number or traceable artifact Repeated prose across multiple docs
Runtime behavior Live harness, logs, code path Observed end-to-end behavior under test Pipeline diagram alone
Theorem / complexity statement Paper, proof sketch, implementation checks Correct statement of proven vs open status Treating an open conjecture as settled
Interpretability bridge External paper + your mapping argument Separate audit of outside claim and your application Counting the bridge as your own measured metric
Section 3

Audit Protocol

Step 1
Extract The Exact Claim
  • Write the number or proposition verbatim.
  • Classify it: metric, runtime claim, theorem, or bridge.
  • Mark whether it is descriptive, causal, or normative.
Step 2
Find The Lowest-Level Source
  • Raw JSON / artifact directory
  • Script or harness
  • Runtime module
  • Paper theorem or external citation
Step 3
Choose The Right Test Mode
  • Rerun: if the harness still exists and inputs are available
  • Inspect: if the artifact exists but rerun is expensive or unclear
  • Demote: if neither rerun nor artifact exists
Step 4
Record Outcome Brutally
  • Pass: claim matches artifact or rerun
  • Revise: claim is directionally right but numbers or scope drifted
  • Demote: claim is narrative-only or unsupported now
For each claim:
1. What page says it?
2. What file generated it?
3. Can I rerun it now?
4. If not, what artifact still proves it?
5. Does the current doc overstate certainty?

Recommended Audit Order

Best Use Of The Next 2–3 Days
Audit In This Sequence
  1. Live runtime behavior first. Validate what the system does now.
  2. Variance probing second. Cleanest experiment family with the best surviving artifacts.
  3. Continuity-blind third. Foundational but more likely to require corpus-path cleanup.
  4. Cascade paper fourth. Split proofs from production-BDG metrics.
  5. Emotion governance last. Strongest as synthesis, not first-pass metrics.
