Section 1

Introduction

The dominant assumption in AI engineering is straightforward: harder tasks require larger models. When a 3B parameter model fails at code auditing, the instinct is to reach for 70B, or GPT-4, or Claude. The model is the bottleneck. Scale is the solution.

This paper presents counter-evidence. We tested five different scaffolding architectures on the same model (llama3.2, 3B parameters) performing the same task (auditing a 2,233-line Python codebase for real bugs). The results span from 0% precision to 80% precision. The model never changed. The scaffold changed five times.

The core insight comes from an unexpected direction. The Belief Dependency Graph (BDG), originally designed for epistemic memory governance in the CORE/Aether system, decomposes complex questions into trees of factual sub-questions. Each leaf question is small enough for a 3B model to answer accurately. The scaffold holds the reasoning structure externally. The model provides atomic verification.

Core Thesis
Question-model fit determines accuracy more than model size
Shape the question to match the model's capability. Hold the reasoning externally. The BDG is a general-purpose reasoning scaffold applicable to any domain where questions can be decomposed into factual sub-questions.

This is not prompt engineering. Prompt engineering adjusts how you ask. Structural decomposition changes what you ask. The distinction matters: a prompt-engineered question still requires the model to hold the full reasoning chain internally. A structurally decomposed question never asks the model to reason at all — only to verify facts.

Section 2

The Progression

Five architectures tested on the same model (llama3.2 3B) and same codebase (CRT heartbeat system, 2,233 lines). Each architecture represents a different theory about why the model was failing.

Architecture 1
Direct Dump — 0%
Feed the entire codebase (15K characters) directly to the model with instructions to find bugs. Result: 20 findings, all false positives. The model fixated on a single function (sanitize_html) and hallucinated issues that did not exist in the code. It never examined 90% of the codebase. The context window was technically sufficient — the model simply could not sustain analytical attention across that much code.
Architecture 2
Chunked + Guard Listing — 0 findings
Split the code into chunks per function. Ask the model to list safety guards present in each chunk. Result: the model rubber-stamped everything. Every function was marked as having appropriate error handling, even functions with obvious missing finally blocks. The model treated the task as a checklist exercise and confirmed whatever patterns it could find, ignoring what was absent.
Architecture 3
Chunked + Risk Challenge — 0%
Split into chunks, but instead of asking for guards, present a specific risk hypothesis and ask the model to confirm or deny. Result: the model agreed with every claim. Present "this function leaks connections" — the model agrees. Present "this function is safe" — the model also agrees. A 3B model at this context size is a yes-machine for leading questions. Sycophancy dominates analytical judgment.
Architecture 4
BDG Tree v1 — 60%
Decompose each function into a tree of factual leaf questions with expected answers. Each leaf asks a single, verifiable question about a code snippet under 200 lines: "Does this function have a finally block?" "Is conn.close() called on all exit paths?" The model answers each leaf. The scaffold aggregates: any UNSAFE leaf makes the branch a RISK. Result: 83 findings, 9/15 validated as real bugs. The model went from useless to genuinely useful by changing what we asked it.
Architecture 5
BDG Tree v2 (Tightened) — 80%
Same BDG tree approach, but with tighter leaf question design: more specific expected answers, smaller code excerpts per leaf, disambiguation of near-synonyms (e.g., "closed" vs. "closed in finally block"). Result: 75 findings, 12/15 validated as real bugs. The 20-percentage-point improvement came entirely from question design refinement, not from model changes or prompt engineering.

Section 3

Atomic Verification

Before building the BDG scaffold, we needed to establish a foundational capability: can a 3B model read code accurately at all? If the model cannot answer simple factual questions about code, no scaffold will help. If it can, then the scaffold only needs to decompose complex questions into simple ones.

Experimental Design

16 factual questions about code snippets under 20 lines. Each question has one objectively correct answer. No reasoning required — only reading comprehension and pattern matching.

Atomic Verification Result

llama3.2 3B • 16 questions • code snippets ≤ 20 lines

94% accuracy (15/16 correct). The single miss: a counting question — the model reported conn.close() appeared 2 times when the correct answer was 3. The model misidentified one occurrence inside a nested conditional. Every other question type — including tricky adversarial questions about variable shadowing and mutable default closures — was answered correctly.

Implication: The 3B model can read code accurately when the context is small and the question is factual. The failures observed in Architectures 1–3 are not reading comprehension failures — they are structural failures of the task framing. The model has the capability. The scaffold must extract it.

The Boundary

llama3.2 3B • 6 code lengths • factual questions

Accuracy remains above 80% through 200 lines. It collapses to 45% at 410 lines — effectively random for binary questions. At 802 lines, the model produces responses that reference code constructs not present in the input (hallucination). The boundary is sharp, not gradual. This defines the hard constraint for BDG leaf design: each leaf question must reference a code excerpt under ~400 lines. In practice, we target under 200 lines to stay in the high-confidence region.

This degradation curve is model-specific. A 7B model would have a different curve. A 70B model would have a different curve. The BDG scaffold design adapts to the model by setting chunk size based on measured accuracy thresholds, not assumed capability.

Design Principle Measure the model's accuracy boundary. Design chunks to stay inside it. The degradation curve is the fundamental constraint. Every other design decision follows from it. For llama3.2 3B on code analysis: 200 lines safe, 400 lines cliff, 800 lines hallucination.
Section 5

BDG Architecture

The BDG tree audit is a two-tier system: one cloud call generates the reasoning structure, then many local calls execute the verification. The cloud model reasons; the local model verifies. Neither does both.

Pipeline

Tree Generation (Holden / Claude Sonnet)
One cloud call per function. Generates a reasoning tree: branches are risk hypotheses, leaves are factual questions with expected safe/unsafe answers.
1 API call per function
Leaf Execution (Mirus / llama3.2)
Each leaf question answered by the local 3B model against a code excerpt under 200 lines. Binary output: SAFE or UNSAFE with short justification.
~1s each, local inference
Branch Aggregation
If any leaf in a branch returns UNSAFE, the branch is flagged as a RISK finding. Conservative propagation: one failure taints the branch.
Logical OR per branch
Finding Compilation
RISK branches collected across all functions. Each finding includes: function name, risk hypothesis, which leaf(s) triggered, and the model's justification.
Structured output
Human Validation
Each finding manually verified against the actual codebase. Verdict: real bug, false positive, or unclear. Severity assigned.

Example Tree

For a function process_heartbeat(), the generated tree might look like:

Function: process_heartbeat()
  Branch 1: "Connection leak risk"
    Leaf 1.1: "Does this function acquire a database connection?"
              Expected: YES (factual)
    Leaf 1.2: "Is conn.close() called in a finally block?"
              Expected: YES for SAFE, NO for UNSAFE
    Leaf 1.3: "Are there early return paths before the close() call?"
              Expected: NO for SAFE, YES for UNSAFE

  Branch 2: "Unguarded type conversion"
    Leaf 2.1: "Is int() called on any variable in this function?"
              Expected: factual check
    Leaf 2.2: "Is the int() call wrapped in try/except ValueError?"
              Expected: YES for SAFE, NO for UNSAFE

  Branch 3: "HTML injection surface"
    Leaf 3.1: "Is user-provided text inserted into HTML output?"
              Expected: factual check
    Leaf 3.2: "Is html.escape() called before insertion?"
              Expected: YES for SAFE, NO for UNSAFE
    Leaf 3.3: "Does the escape call include quote=True?"
              Expected: YES for SAFE, NO for UNSAFE

Each leaf is a single factual question. The model never needs to reason about whether a pattern is dangerous — that judgment is encoded in the tree structure by the cloud model. Mirus only needs to verify what the code does, not whether what it does is safe.

The separation is the key insight: risk identification (what could go wrong) requires reasoning and context — a cloud-scale capability. Fact verification (does this code do X) requires reading comprehension — a 3B-scale capability. The BDG scaffold places each task at the right level.

Finding Patterns

Pattern 1: Systemic Bugs Connection leaks found across 8 functions — same root cause, replicated everywhere The BDG scaffold found the same conn.close()-not-in-finally pattern in 8 separate functions. A human auditor finding one instance would search for others. The BDG scaffold finds them independently because each function gets its own tree. This is structural thoroughness — the scaffold cannot skip functions or get bored.
Pattern 2: Cross-Layer Logic Bugs LLM prompt references data the input feed never provides Finding #11 (prompt asks for post_id but feed has no IDs) is a logic bug that spans two layers of the system. The BDG leaf question was: "Does the data structure passed to this function contain a field called post_id?" The model correctly answered NO. The tree structure identified that the prompt template referenced this field. The scaffold connected the two facts. The model never had to.
Pattern 3: False Positive Profile All three false positives required architectural context beyond the function Thread safety (#13) requires knowing the deployment model. Config validation (#14) requires knowing the startup sequence. Cache bounds (#15) requires seeing code in a different file. The false positives are precisely the cases where per-function analysis is insufficient — they define the scaffold's honest boundary.

The BDG scaffold found a bug that manual review had missed. Total cost of the audit: one cloud API call for tree generation plus ~184 seconds of local inference.
Section 7

Hybrid Leaves

The BDG scaffold in code auditing uses a single leaf type: LLM verification. But when we applied the same structural decomposition principle to other domains, we discovered that mixing leaf types consistently outperforms any single method.

Intent Routing

Three Leaf Types Compared

Intent classification • CRT routing pipeline • 200 test queries

Pure regex matching: ~70% accuracy. Fast, deterministic, but misses semantic intent variations.
Pure BDG LLM classification: 65–70% accuracy. Handles semantic variation but hallucinates categories.
Hybrid (regex + embedding + LLM tiebreaker): 93% accuracy. Regex handles known patterns. Embeddings catch semantic similarity. LLM only invoked for ambiguous cases that both miss.

Belief Verification

Contradiction Detection Approaches

Belief pair verification • CRT memory system • 100 contradiction pairs

Pure LLM judgment: 40% accuracy. The model over-detects contradiction, flagging stylistic differences as semantic conflicts.
Hybrid with LLM: 38% accuracy. Adding structural features did not compensate for LLM noise — the LLM signal dominated.
Structural only (slot extraction + embedding similarity + metadata comparison): 88% accuracy. No LLM calls. 0.2s per pair.

The Hybrid Principle

LLM verification Ambiguous cases, novel patterns ~1s Sycophancy, hallucination, over-detection

Hybrid Leaf Principle
Use regex for patterns, embeddings for similarity, LLM only as tiebreaker
The LLM is the most expensive and least reliable leaf type. Promote it to the role it actually excels at — handling the cases that deterministic methods cannot resolve — rather than using it as a universal hammer.
Section 8

Structural Tension

The hybrid leaf experiments revealed something unexpected. When we removed the LLM from belief verification entirely, accuracy increased. This led to a more fundamental question: can you measure contradiction without any language model at all?

The Structural Approach

Instead of asking "do these beliefs contradict each other?" (a judgment call), we decompose the question into measurable sub-questions:

Slot Extraction Extract structured fields from each belief: subject, predicate, object, temporal marker, confidence Regex-based extraction from belief text into a canonical slot format. "Nick works at a design studio" becomes {subject: "Nick", predicate: "works_at", object: "design studio", temporal: null}. No LLM required.
Embedding Similarity Compute cosine similarity between belief embeddings High similarity (>0.85) between beliefs with different slot values indicates potential tension. Low similarity (<0.5) means the beliefs are about different topics. The embedding provides topical proximity without semantic judgment.
Metadata Comparison Compare temporal markers, trust scores, source provenance, and update frequency Two beliefs about the same topic with divergent trust trajectories indicate unresolved tension. A belief corrected multiple times has higher tension than one stated once. Metadata encodes history without requiring the model to remember it.

Structural Tension Result

Slot + embedding + metadata • 0 LLM calls • 100 belief pairs

88% accuracy at 0.2s per pair. No language model invoked. The structural approach correctly identifies tension between beliefs that share a subject-predicate but diverge on object, temporal markers, or trust trajectory. It does not identify beliefs that are semantically contradictory but structurally different (e.g., "Nick is a vegetarian" vs. "Nick ordered a steak") — that 12% gap is where LLM judgment would add value, if used as a final tiebreaker rather than a primary detector.

Reframing
The question is not "do these beliefs contradict?" but "what is the tension between them?"
Contradiction is binary. Tension is measurable. A 0.72 tension score between two beliefs about employment status tells you more than a boolean "contradicts: true". The scaffold measures tension from structure. Judgment, if needed, is applied at the end, not the beginning.

This is the BDG principle applied to its own domain. Instead of asking the model a complex judgment question ("are these beliefs contradictory?"), we decompose it into factual sub-questions ("do these beliefs share a subject?", "do they have different objects?", "what is their embedding similarity?") and let the scaffold combine the answers.

Section 9

Implications

The results across three domains (code auditing, intent routing, belief verification) converge on a single design principle: question-model fit.

The Principle

Every model has a capability boundary — a region of task complexity where its accuracy is high. Outside that region, accuracy degrades rapidly (as demonstrated by the degradation curve in Section 4). The traditional response is to use a larger model with a wider capability boundary. The BDG alternative is to reshape the task to fit inside the smaller model's boundary.

Implication 1 Scaffold design is a distinct engineering discipline The 0% to 80% improvement is not prompt engineering. It is not fine-tuning. It is not model selection. It is task decomposition: a structural transformation of the problem that changes what the model is asked to do. This is a learnable, repeatable skill that applies across domains.
Implication 2 Small models are underestimated because they are misused A 3B model asked to "audit this code for bugs" performs at 0%. The same model asked "does this function have a finally block?" performs at 94%. The model did not change. The question changed. Much of the perceived capability gap between small and large models may be a question-model fit gap, not a capability gap.
Implication 3 The BDG scaffold is domain-general Any verification task that can be decomposed into factual sub-questions is a candidate for BDG scaffolding. Medical diagnosis: "does the patient have symptom X?" Legal review: "does clause Y contain term Z?" Financial audit: "does this transaction exceed threshold W?" The structure transfers. The leaves change.
Implication 4 Cost follows the scaffold, not the model The BDG code audit used one cloud API call (tree generation) and 184 local inferences (~3 minutes of local compute). The direct-dump approach used the same model for the same time with 0% precision. The cost is identical. The value is entirely determined by the scaffold. Scaling up to a larger model without fixing the scaffold is waste.
Implication 5 Reasoning should be held externally, not generated internally The BDG tree holds the reasoning chain (risk hypothesis, decomposed questions, aggregation logic) outside the model. The model never generates reasoning — it only verifies facts. This eliminates the most common failure modes of small models: loss of thread, hallucinated reasoning chains, and sycophantic agreement with complex premises.

The Design Methodology

To apply BDG scaffolding to a new domain:

1. MEASURE the model's accuracy boundary
   - Test factual questions at increasing complexity
   - Identify the cliff point (accuracy < 60%)
   - Set maximum chunk size to stay in the >80% region

2. DECOMPOSE the target task into a tree
   - Root: the complex question you want answered
   - Branches: independent risk/hypothesis categories
   - Leaves: factual sub-questions answerable within the chunk limit

3. ASSIGN leaf types by question characteristics
   - Deterministic patterns → regex
   - Semantic similarity → embeddings
   - Factual verification → LLM (within chunk limit)
   - Ambiguous / novel → LLM tiebreaker (last resort)

4. AGGREGATE using conservative propagation
   - Any failure in a branch → branch is flagged
   - Unclear results → escalate, do not resolve

5. VALIDATE on ground truth
   - Measure precision (real findings / total findings)
   - Identify false positive patterns
   - Tighten leaf questions iteratively

Central Result
The intelligence is in the decomposition, not the model
A 3B parameter model that cannot audit code can verify facts about code. A scaffold that decomposes auditing into fact verification makes the 3B model an effective auditor. The capability was always there. The structure was missing.

This suggests a broader reframing of the capability scaling question. Before asking "do we need a larger model?", ask: "have we shaped the question to fit the model we have?" The degradation curve is the diagnostic tool. The BDG tree is the structural intervention. The hybrid leaf principle determines which verification method to use at each node. Together, they form a repeatable methodology for making small models competent at tasks they appear to fail.

The model never changed. The scaffold changed five times. That is the finding.
