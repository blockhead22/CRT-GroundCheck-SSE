Slots as
the Substrate Anchor

An inversion of the current memory-first architecture: make slots the typed primitive, treat memories as observations on slots.

Aeteros Research • 2026-05-01

Stoned-Nick insight, captured for sober-Nick. Not a commitment to refactor — a design idea worth preserving.

Slot Anchor
The insight

Everything is anchored

Tonight the bench on the GPT corpus surfaced a question larger than the bench itself. The slot extractor produces structured tags (location: Milwaukee, employer: Microsoft) at write time. After that, the slot is mostly forgotten. The memory becomes a free-text node in the BDG; the BDG's edges are between memories; trust and cascade flow through memory-to-memory relations. Slots decorate the substrate but don't organize it.

The insight: slots should be first-class. Memories should be derivative. Every belief is a typed observation on some slot at some point in time. The dependency graph is a graph over slots, not over text. "Everything is anchored" means every belief has a typed channel it sits in, and corrections cascade through slot relations rather than through textual similarity.

Today

Memory-first

  • Memory is the BDG node
  • Slots produced at write time, mostly discarded
  • Edges: SUPPORTS / DERIVED_FROM / CONTRADICTS / SUPERSEDES between memory nodes
  • Trust attaches to memories
  • Cascade flows through textual relations
  • Slots are decoration
Proposed

Slot-first

  • Slot is the typed channel (the anchor)
  • Memory is an observation: (slot, value, timestamp, source)
  • BDG edges between slot states, not text
  • Trust attaches to slot:value tuples
  • Cascade flows along typed slot relations
  • Memory is the audit trail
Why it might be right

The cleaning effect

Three things get cleaner under the slot-first model.

Contradiction becomes typed. Today, "I live in Milwaukee" contradicting "I live in Seattle" requires the contradiction layer to extract slots from both at comparison time. Under slot-first, the contradiction is a slot-state transition that's detected at write time without re-extraction. The slot is the contradiction surface.

Cascade has structure to flow through. Today the BDG has edges between memories that share textual similarity. Under slot-first, edges encode genuine epistemic relations: employer depends on location if the employer is geographically tied. Correcting location cascades to employer through a typed edge, not through cosine.

The system can hold its own audit trail. Memory becomes the journal of slot-state changes. Lineage queries ("why do I believe employer=Microsoft") walk the journal of that slot, not arbitrary text edges.

Three extensions this enables

Slots beyond personal facts

If slots are the primitive, the namespace can extend without changing the substrate.

user:* — personal facts (today)

The current scope. user:location, user:employer, user:favorite_color. Same as ExtractedFact today. No change required.

code:* — codebase observations

The substrate watches a dev session and learns: code:my_project:func_x:co_occurs_with = {slot_reversal_case, contradiction_layer}. Temporal too — code:foo:return_type changes when the source changes. aether_lineage on a code slot answers "why do I believe foo() returns Result[T]" with the commits that established it.

session:* — behavioral state

The substrate watches turn signatures and infers: session:focus_level=scattered, session:tone=frustrated, session:demand=brevity. These slots have higher decay rates and come from a windowed observer rather than per-turn extraction. They fire BDG actions — switching prompt strategies, surfacing earlier-said-this warnings — rather than just describing.

Each namespace is a different ingestion pipeline (regex, LLM, code-watcher, behavioral observer) writing into the same substrate primitive. The contradiction layer, cascade, trust evolution, and lineage all work uniformly.

The cache-and-codify pattern

Regex distillation from LLM extraction

Independently useful and trivially compatible with the slot-first model. Three stages:

  • Discovery. When the LLM extracts a slot the regex bank missed, log (text → slot:value) to ~/.aether/learned_slots.jsonl.
  • Promotion. When N occurrences of a mapping share enough surface structure, distill a regex from the surface forms and add it to a learned regex bank.
  • Custodial. Learned regex catches the codified pattern next time. LLM only fires on what neither bank handles. The system gets cheaper over time.

Failure mode is bounded: the curated regex bank is never modified, only an additive learned bank that can be wiped with one env var. The LLM is the oracle, the regex is the student.

Tradeoffs

What this costs

Pro · Cleaner contradiction

Slot-state transitions are structural; the meter doesn't need to re-extract from prose at every comparison.

Pro · Typed cascade

BDG edges encode epistemic relations between channels, not text-similarity proxies. The 599-node BRG becomes interpretable.

Pro · Namespace extensibility

Code slots, behavioral slots, meta slots all use the same primitive. New domains are new namespaces, not new architecture.

Pro · Behavioral slots become tractable

Inferred-from-aggregate state has a place to live. session:focus_level isn't a memory hack; it's a typed slot with a decay rate.

Con · Major refactor

Inverting the BDG primitive is a v0.14 → v0.15 architectural pivot, not a patch. Migration of the existing 180-memory substrate is non-trivial.

Con · Slot vocabulary becomes load-bearing

Today the regex extractor is best-effort. Under slot-first, an unknown slot means an un-anchored belief. The vocabulary needs a curation discipline.

Con · LLM extraction on the critical path

For namespaces beyond the curated regex (codebase, behavioral), LLM extraction is required. That changes cost and latency profiles in ways the current README doesn't describe.

Con · Memory-as-journal needs more storage

Every slot transition becomes a memory entry. The substrate grows faster. Current rotation/retention policies need rethinking.

Decision

Status: captured, not committed

Not a refactor commitment

This note exists so the insight survives the night. Sober-Nick can read this and decide whether to pursue it as a v0.14 → v0.15 architectural pivot. If yes, the cache-and-codify pattern is the natural first step (it's additive and compatible with both architectures). If no, the existing memory-first model continues to work and this note is filed under "design ideas considered."

The bench tonight (94.92% paraphrase-blind floor on archival corpora) shows the existing model has a real limitation that motivated this thinking. The LLM extractor stub aether/memory/llm_extract.py can be used to test slot-first ideas incrementally without inverting the primitive.

First-class slots, second-class memory. The system doesn't change shape; it changes which thing is the anchor.
