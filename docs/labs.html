Section 1

Why Labs Exist

Manual testing produced inconsistent results. Restarting the system between tests introduced variables. Each session's conversation context bled into the next. We couldn't tell whether a detection failure was a real bug or an artifact of the testing method.

Labs solve this by running controlled, repeatable experiments against the live system. Each lab:

  1. Seeds known facts to establish a controlled baseline
  2. Sends structured probes with predetermined expected outcomes
  3. Queries the pipeline state after each probe (ledger, trust deltas, metadata flags)
  4. Scores pass/fail against expected behavior
  5. Generates a frozen HTML report that can be referenced, compared, and cited

The result is a single run that produces a complete picture. No relaunching. No context bleed. No ambiguity about what passed and what didn't.

Labs are not unit tests. They test the full production pipeline end-to-end — intent routing, memory storage, slot extraction, contradiction detection, ledger creation, trust demotion, and response metadata. A lab failure means the production system would fail on the same input.

Section 2

Contradiction Pipeline Lab

The Problem Being Tested

The CORE architecture claims to detect when a user contradicts a previously stored fact — for example, changing their favorite color, their employer, or their name. Live testing on April 7, 2026 revealed that contradiction detection never formally fired despite the system recognizing conflicts in its generated responses. Three root causes were identified:

  1. Intent routing bypass: The regex intent classifier misclassified declarations ("My favorite drink is water") as broad_recall queries, routing them through the agent loop which has no contradiction pipeline.
  2. Early memory promotion: New memories were promoted from provisional to confirmed before the slot-level contradiction check ran.
  3. Agent loop bypass: The agent loop path (GPT-4.1) generates responses without running the contradiction detection code in crt_rag.py.

The Fix

A write-path contradiction check was added to crt_memory.py:store_memory(). This is the single convergence point every memory passes through, regardless of routing. The existing slot exclusivity loop (which already demotes trust on conflicting exclusive slots) now also creates a contradiction ledger entry. The fix:

  • Fires regardless of intent routing (agent loop, legacy pipeline, any future path)
  • Uses memory_facts table for structured slot comparison (not text search)
  • Creates ledger entries with contradiction_type=slot_reversal
  • Deduplicates against existing entries to prevent double-recording
  • Does not change the existing trust demotion behavior — additive only

What the Lab Tests

The full chain: user input → slot extraction → contradiction detection → ledger entry → trust demotion → metadata flag.

10 probes total:

  • 5 should-fire probes — exclusive slot reversals (name, location, age, employer, favorite color). Includes short corrective statements, long narrative blocks with contradictions buried mid-paragraph, and contextual declarations that never use the explicit "my X is Y" pattern.
  • 5 should-NOT-fire probes — additive slots (hobbies), questions, reinforcements of existing facts, third-party facts about other people, and long multi-hobby text blocks. These test for false positives.
Section 3

Extraction Escalation

The write-path fix works when slot extraction succeeds. The bottleneck is upstream: can the system extract structured facts from natural language? Three extraction tiers were tested in sequence to establish which capability level is required for production-grade contradiction detection.

Tier Method Should-Fire Should-NOT-Fire Status Finding
1. Regex extract_fact_slots (pattern matching) 2/5 5/5 Tested Catches direct "my X is Y" patterns. Fails on indirect phrasing, buried context, contextual declarations. Zero false positives.
2. Local LLM TwoTierFactSystem (llama3.2 via Ollama) Untestable Failed Added 30–250s latency per memory write. Caused 300s timeouts on simple seed facts ("I'm 34 years old"). Pipeline already runs 35–50s per message; local LLM extraction made it unusable.
3. Cloud gpt-4o-mini via cloud_features.classify_slot() Not yet isolated Next Infrastructure exists. First test exposed a critical issue: cloud demotion operates on text search, not structured slots, and cascaded destructively through shared memory. Requires isolated DB before retesting.

The escalation establishes an empirical progression: regex is fast but narrow, local LLM is too slow, cloud has the capability but needs architectural safeguards. This is not a preference — it's a measured necessity.

Section 4

Key Findings

1. The write-path fix works

When extract_fact_slots successfully extracts a slot, the full chain fires. T3 (age 34→35) produced: metadata.contradiction_detected=true, ledger entry contra_1775627760140_8310 with type revision, trust demotion from 0.701 to 0.697. This is the first time the formal contradiction pipeline completed end-to-end in production.

2. Zero false positives

All 5 should-NOT-fire probes passed. Additive slots (hobbies), questions about locations, reinforcement of existing facts, third-party facts, and long multi-topic text blocks all stayed silent. The system does not over-trigger.

3. Extraction is the bottleneck, not detection

Three of five should-fire probes failed because regex extraction couldn't parse the input:

  • T1 (name): "Actually, my name is Adrian now" — corrective phrasing with "now" confused the extractor
  • T4 (employer): "I actually left Anthropic about a month ago and joined OpenAI" — buried in a 70-word daily narration paragraph
  • T5 (favorite_color): "It's definitely my favorite color now, green" — contextual declaration without the "my favorite X is Y" pattern

4. The LLM already knows

In every failed should-fire case, Claude's generated response correctly identified the contradiction. T4's response began: "Six in a row. You just embedded 'left Anthropic, now at OpenAI' inside a paragraph of mundane daily detail." T5's response noted: "I have FACT: User.favorite_color = blue stored at trust 1.00. You just told me it's green." The model extracts the facts perfectly — it just doesn't write them to the slot system.

5. Cloud demotion is destructive without isolation

The first cloud extraction test (before DB isolation) triggered a cascade that demoted 81 real memories. See Incident Report below. This exposed a critical architectural flaw: the cloud governance code in routes/chat.py uses LIKE '%name%' text search instead of memory_facts table lookups, and applies a flat 0.4× trust multiplier with no damping or depth bounds. The BDG cascade system (which has damping, depth bounds, and proportional impact) was never consulted.

Section 5

Incident: Shared Memory Cascade

April 8, 2026 — Production memory damaged by lab test. Cloud slot classification enabled for lab v3 run. Seed message "My name is Marcus" triggered gpt-4o-mini extraction → name=Marcus, exclusive=true → cloud governance demotion searched ALL memories for text containing "name" → 81 memories demoted (trust × 0.4), including core identity memories ("My name is Nick" dropped from 1.00 to 0.40). Damage was reversed by manual trust restoration and lab artifact deprecation. Root cause: lab used shared production database, and cloud demotion used text search instead of structured slot comparison.

What Went Wrong

  1. No database isolation. The lab harness sent test messages to a unique thread_id but all threads share crt_memory_shared.db. Thread isolation does not equal memory isolation.
  2. Text search, not slot search. The cloud governance code at routes/chat.py:4971 uses WHERE LOWER(text) LIKE ? to find conflicting memories. This matched 81 memories containing the word "name" anywhere in their text, not just memories with memory_facts.slot = 'name'.
  3. No damping. The demotion applied a flat trust × 0.4 to every match. The BDG cascade system (which has configurable damping, depth bounds, and proportional impact) was not used.
  4. No rollback. The demotion was not logged through the standard trust_log with a reversible reason. Manual SQL restoration was required.

Remediation

  • 8 core identity memories manually restored to original trust values
  • 13 lab artifact memories deprecated with reason lab_artifact_cleanup_20260408
  • 3 lab seed memories deprecated with reason lab_seed_cleanup_20260408
  • Routing settings reverted to local_only until isolation is implemented

Required Before Next Cloud Test

  1. Isolated lab database: Lab harness must create and use its own SQLite DB, not crt_memory_shared.db
  2. Cloud demotion must use memory_facts: Structured slot comparison, not text search
  3. Demotion must go through BDG cascade: With damping, depth bounds, and proportional impact
Section 6

Where This Goes

For the Pipeline

The write-path contradiction fix is validated and stays. The next step is cloud extraction with an isolated database. If cloud extraction achieves 5/5 on should-fire probes, the pipeline gains production-grade contradiction detection for the first time. The cloud governance demotion code needs to be rewritten to use memory_facts and BDG cascade before it can be enabled in production.

For the Research

The escalation chain (regex → local LLM → cloud) is itself a research finding. It demonstrates that contradiction detection is not a single capability — it's a stack: extraction quality determines detection quality. The bottleneck is always the weakest extraction layer, not the detection logic. This maps directly to the paper's argument: governance requires more than memory — it requires structured understanding of what the memory contains.

For Governance Validation

Test 1.1 (Contradiction Detection) currently scores 1 on the governance validation scorecard. A successful cloud extraction lab run would move it to score 2. Combined with the existing Tier 1 scores (5/6 at score 2+), this would meet the minimum threshold for a defensible draft.

For the System

The incident exposed that the cloud governance layer operates outside the BDG cascade system. This is a structural gap: two independent demotion mechanisms (write-path slot exclusivity and cloud governance text search) that don't coordinate. The architectural target is a single demotion pathway that always flows through the BDG with damping, regardless of source.
